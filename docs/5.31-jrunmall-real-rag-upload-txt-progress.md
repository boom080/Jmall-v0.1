# 5.31 Jrunmall 真实 RAG 上传 txt 改造进度

## 1. 为什么去掉 fake RAG

旧链路的知识库数据主要来自 Python fallback hardcode 和 `ai-services/data/merchant_ai_store.json` 文件快照，前端和 Java 在远端不可用时还会展示 fallback 知识库。商品文案生成虽然会带 `knowledgeBaseId`，但检索只在文件里的 chunk embedding 上做内存相似度，不是 PostgreSQL + pgvector 的真实 RAG。

这会导致三个问题：

- 页面看起来有知识库，但不是用户上传产生的数据。
- 文案生成无法证明使用的是当前知识库的 `chunks.embedding`。
- 旧文件里出现过 `???????` 这类乱码内容，继续保留会污染验证结果。

本次目标是改成：网页上传 txt -> Java adapter -> Python ingest -> PostgreSQL/pgvector -> 商品文案按 `knowledgeBaseId` 检索 chunk。

- `POST /api/merchant/knowledge-bases/upload-txt`
- 代码：`knowledge_bases.py -> KnowledgeBaseService.upload_txt_knowledge_base`

Python ingest 步骤：

1. 校验 multipart/form-data。
2. 创建 `knowledge_base`。
3. UTF-8 读取 txt。
4. 清洗文本。
5. 计算 `content_hash` 防重复。
6. 创建 `knowledge_document`。
7. 按配置切 chunk。
8. 生成 chunk embedding。
9. 写入 `knowledge_chunks`。
10. 返回 `knowledgeBaseId`、`documentId`、`chunkCount`、`embeddingProvider`、`status`。

## 5. chunking 规则

- 支持中文 txt。

## 7. product-copy 如何使用 RAG

前端生成文案请求必须带：

- `modelProvider`
- `modelName`
- `knowledgeBaseId`
- 商品标题、分类、卖点、目标风格

Java 会透传 `knowledgeBaseId` 到 Python，默认 Python 接口为 `POST /api/product-copy/generate`。旧 `/api/mock/product-copy` 仅保留兼容，不再作为 Java 默认路径。

Python workflow：

1. 根据商品信息构造检索 query。
2. 调用 `RagRetriever.retrieve(query, knowledge_base_id, top_k)`。
3. retriever 先生成 query embedding，再只在指定 `knowledge_base_id` 下检索 `knowledge_chunks`。
4. 使用 pgvector `<=>` 排序。
5. 将命中 chunk 写入 prompt 的【电商知识库参考资料】区。
6. 有命中时返回 `response_source = rag`、`usedChunks`、`citations`。
7. 无命中时返回 `response_source = no_rag_fallback`，不阻断普通文案生成。

### RAG 不等于事实来源

商品文案生成时，RAG 命中的 txt chunk 只作为写法结构、表达风格和参考资料，不代表当前商品一定具备 chunk 里的参数、材质等级、适用人数、认证、售后、功效或价格活动。

事实优先级以本次商品输入为准：

- 商品输入没有提供的信息，不生成确定事实。
- 不主动补充未提供的认证、销量、排名、保修、适用人数、材质等级。
- 信息不足时写入 `pendingMerchantConfirmations`，用“请商家确认……”表达。
- 类目常识只能用于组织文案，不能把一般经验写成当前商品的确定卖点。
- 如果模型输出了“减少油烟”“永不粘锅”“3-5人适用”“导热均匀”“耐用抗腐蚀”等高风险表达，但商品输入没有证据，服务层会改成保守表达或放入待商家确认信息。

prompt 证据区格式：

```text
【电商知识库参考资料】
1. 来源：xxx
相关度：xxx
内容：xxx

【生成任务】
结合商品信息、目标人群、平台风格和以上知识库资料，生成：
1. 商品标题
2. 3-5 条短卖点
3. 详情页文案
4. 短视频口播文案
5. 合规风险提醒
6. 待商家确认信息
```

## 13. 真实 embedding 切换检查结论（2026-06-01）

### ai-services 实际读取哪个环境变量文件

`ai-services/app/core/config.py` 使用 `pydantic-settings`，配置为：

```python
env_file=("../.env.local", ".env.local", ".env")
```

结合 `scripts/start-ai-services.bat` 的启动方式，实际情况是：

1. 启动脚本先在项目根目录读取 `.env.local`，并把非空变量写入当前进程环境变量。
2. 然后脚本 `cd ai-services` 启动 `uvicorn`。
3. Python Settings 再从 `ai-services` 工作目录读取：
   - `../.env.local`，即项目根目录 `.env.local`
   - `ai-services/.env.local`
   - `ai-services/.env`

本次检查时 `ai-services/.env.local` 不存在，项目根目录 `.env.local` 中 RAG embedding 相关变量为空，因此当前实际配置仍是 mock embedding，`DATABASE_URL` 也未生效。

### 当前数据库 vector 字段是否匹配

本次检查的本地 PostgreSQL 容器是 `jrunmall-postgres-local`，数据库是 `jrunmall_ai`，schema 是 `jrunmall_merchant_ai`。

实际 `knowledge_chunks` 当前列结构中没有 `embedding vector`，而是旧列：

```text
embedding_json text
embedding_provider varchar(64)
```

同时当前库里没有查到已安装的 `vector` extension。也就是说，当前数据库字段不匹配 `RAG_EMBEDDING_DIMENSION=1024`，甚至还不是 pgvector 检索所需的新表结构。

`resource/db/5.6-rag-ingestion.sql` 里的目标结构是 `embedding vector`，但不是 `vector(1024)`。如果要固定接 `text-embedding-v4` 的 1024 维向量，建议把字段建成或迁移成 `vector(1024)`，这样数据库会在写入时直接校验维度。

### 最小修复方案

本地开发可以清空旧 mock 知识库；只清理 PostgreSQL 的 `jrunmall_merchant_ai` RAG schema，不动 MySQL 商品业务表，不删除非 RAG 业务数据。

先确认 PostgreSQL 端口以 `docker ps` 为准。本次检查容器映射是宿主 `5433 -> 5432`。

建议手动执行以下 SQL：

```sql

create schema if not exists jrunmall_merchant_ai;

truncate table
  jrunmall_merchant_ai.knowledge_chunks,
  jrunmall_merchant_ai.knowledge_documents,
  jrunmall_merchant_ai.knowledge_bases

  drop column if exists embedding_json;

alter table jrunmall_merchant_ai.knowledge_chunks
  add column if not exists char_count integer not null default 0,
  add column if not exists token_count integer,
  add column if not exists metadata jsonb not null default '{}'::jsonb,
  add column if not exists embedding vector(1024),
  add column if not exists embedding_provider varchar(96) not null default '';

  alter column embedding type vector(1024)

```

如果本地表结构太旧，最干净的做法是只重建 RAG 三张表：

```sql
drop table if exists jrunmall_merchant_ai.knowledge_documents cascade;
```

```sql
  alter column embedding type vector(1024)
  using null;
```

### 为什么切换维度后必须重新上传知识库

RAG 检索时会把“查询文本”的 embedding 和“知识库 chunk”的 embedding 做向量距离计算。这个计算要求两边向量来自同一个 embedding 模型，并且维度一致。

旧 mock chunks 是 8 维，真实 `text-embedding-v4` 配置是 1024 维。8 维向量不能和 1024 维向量做有效相似度比较；pgvector 固定为 `vector(1024)` 后也会拒绝写入或比较 8 维向量。

即使数据库字段是不限维的 `vector`，旧 mock 向量也不能继续用，因为 mock embedding 是哈希生成的开发测试向量，不代表真实语义空间。真实 query embedding 与旧 mock chunk embedding 不在同一个向量空间里，检索结果没有语义意义。

因此切换到真实 embedding 后必须清空旧 mock chunks，并重新上传 txt，让所有 chunk 使用 `text-embedding-v4` 重新生成 1024 维 embedding。

## 14. 从 mock embedding_json 升级到 pgvector vector(1024)

### 14.1 旧 RAG 表问题

旧本地 RAG 表 `jrunmall_merchant_ai.knowledge_chunks` 使用过 `embedding_json text` 保存 mock 向量。这个字段只能存文本 JSON，不是 pgvector 的向量类型，不能被 PostgreSQL 使用 `<=>` 做正式向量相似度检索，也不能建立 pgvector 的 HNSW/IVFFLAT 向量索引。

mock 阶段的向量默认是 8 维，真实 `text-embedding-v4` 本地目标配置是 1024 维。8 维 mock 向量和 1024 维真实向量维度不同，且不在同一个语义向量空间内，不能混用。切换到真实 embedding 后必须清空旧 mock 知识库并重新上传 txt，让所有 chunk 重新生成 `vector(1024)`。

### 14.2 新 pgvector 表结构

新增本地迁移脚本：

```text
resource/db/5.7-rag-pgvector-1024.sql
```

该脚本只处理 PostgreSQL 的 `jrunmall_merchant_ai` schema，执行内容包括：

- `create extension if not exists vector;`
- `create schema if not exists jrunmall_merchant_ai;`
- drop/recreate `knowledge_chunks`、`knowledge_documents`、`knowledge_bases`
- `knowledge_chunks.embedding vector(1024)`
- `knowledge_chunks.metadata jsonb`
- `knowledge_base_id`、`document_id` 普通索引
- `embedding vector_cosine_ops` 的 HNSW 索引

HNSW 不需要预先训练数据，适合作为本地数据增长后的 pgvector 检索索引。检索 SQL 仍然必须带 `knowledge_base_id` 条件，避免跨知识库命中。


### 14.4 Python ingest/retriever 约定

Python ingest 正式写入字段是：

```text
jrunmall_merchant_ai.knowledge_chunks.embedding
```

写入时使用：

```sql
cast(:embedding as vector)
```

retriever 正式检索使用：

```sql
chunk.embedding <=> cast(:query_embedding as vector)
```

并且必须包含：

```sql
chunk.knowledge_base_id = :knowledge_base_id
```

`embedding_json text` 不再作为正式检索来源；如果以后为了兼容旧数据临时保留，也只能作为历史字段，不能作为 pgvector 检索字段。

### 14.5 维度校验

`RAG_EMBEDDING_DIMENSION=1024` 时：

- mock provider 也会返回 1024 维，便于本地测试数据库结构。
- openai-compatible provider 会请求 1024 维并返回 provider 名 `openai-compatible`。
- 如果 provider 返回维度与 `RAG_EMBEDDING_DIMENSION` 不一致，`EmbeddingService` 会抛出清晰错误，避免错误向量写入数据库。

### 14.6 配置位置

真实 embedding 配置应写入：

```text
ai-services/.env.local
```

`.env.example` 和 `ai-services/.env.example` 只是模板，不能写真实 API Key。`ai-services/.env.local.example` 提供示例，API Key 使用 `你的百炼APIKey` 占位。
