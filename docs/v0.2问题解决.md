# Jmall v0.2 问题解决

> 版本状态：开发中（M1、M2、M3 已完成）  
> 版本目标：把“技术可运行”推进到“商品可以安全保存和发布”  
> 核心原则：先补齐，再生成，检查后发布

## 1. 少量输入仍然生成完整商品内容

### 遇到的问题

当前用户只填写商品名称和品类就能启动完整 Agent 流程，但文案 Agent 又被要求生成多个标题、卖点、详情页和视频脚本。模型获得的事实不足，却必须输出完整结构，最终只能产生大量通用内容或待确认占位文案。

### 使用的技术

- 新增不调用大模型的确定性输入体检，将商品名、品类、商品事实/规格和目标人群作为完整生成的四项硬门槛；使用场景是提高理解度的加分项，不会强迫每类商品都填写。
- 同时支持两条输入路径：用户可在“商品说明”中写完整长段落，也可填写现有的规格、目标人群和使用场景字段。
- 前端先调用免费的 `/api/ai/input-assessment` 预检；不足时只展示已理解信息、缺失项和最多 3 个追问，不进入付费编排。
- Python LangGraph 的入口增加同样的硬门禁，避免绕过前端直接调用完整编排；单独文案接口也复用此门禁。
- 结构化规格不是“非空就通过”：至少要有两项去重后的有效事实，或一条包含事实标记/计量值的具体描述；单字、重复内容、测试占位符和纯主观词无法绕过门禁。
- Java 付费编排接口会在扣费前再执行一次服务端预检；直接调用非流式或 SSE 接口也不能绕过门禁导致无效扣费。
- 生成按钮在预检和 Agent 执行期间锁定，并在事件入口增加重入保护，避免双击重复启动任务和重复扣费。
- 结构化规格、目标人群和使用场景会全部传入编排 Agent 提示词，不丢失用户已经填写的信息。

### 达到的效果

- 只有商品名和品类时，系统返回 `needs_input`，不启动市场调研、RAG、文案、合规和风格 Agent；页面预检也不扣除金币。
- 包含商品事实、目标人群和使用场景的完整长段落可以通过；等价的结构化表单输入也可以通过。
- 输入检查服务不可用时采取失败关闭，不会降级为盲目生成。
- 对抗测试已覆盖重复长句、重复规格、无效人群、测试占位符、零宽字符和纯 Emoji 输入。
- M3 完成后的全量回归中，Python 190 项、Java 51 项、前端 34 项测试全部通过。

## 2. 系统只提示“信息不足”，不会有效追问

### 遇到的问题

当前待确认项大多是通用提醒，例如“请补充规格”，不能帮助用户快速判断应该填写什么。

### 计划使用的技术

- 信息体检节点根据品类和已知事实生成最多 3 个高价值问题。
- 问题使用结构化 Schema 返回，前端可以把答案直接回填到商品事实。
- 用户回答后只重新执行信息体检，不重复运行市场调研和长文生成。

### 目标效果

- 问题从“请补充更多资料”变成“枕芯和外层分别是什么材质”。
- 用户用一至两轮问答即可达到基本生成门槛。
- 减少无效模型调用和重复等待。

## 3. 用户没有商品图片时无法继续

### 遇到的问题

当前商家可以上传图片，但无图时只显示品类占位图。已有图片生成代码没有接入真实用户流程，也没有三图搜索和选择能力。

### 使用的技术

- 新增独立的 Image Scout API：浏览器调用 `/api/ai/images/candidates`，Java 登录态代理转发到 Python `/api/agent/images/candidates`，图片检索不扣金币。
- Python 侧增加可替换的 `ImageSearchProvider`。首个真实实现通过 SerpAPI 获取结构化 Google Images 结果，不抓取 Google 页面；没有 Key 时明确返回 `provider_unavailable`，不会用占位图伪装搜索成功。
- 搜索前复用确定性输入体检。只有“商品名称 + 品类 + 真实事实 + 目标人群”达到 `ready` 才会请求外部图片服务，模糊输入不会消耗搜索额度。
- 搜索词合并商品名、品类、已确认规格、目标人群和说明；按 Provider 原始相关性顺序去重，最多返回 3 张，相关结果不足时不补无关图片。
- 候选统一返回缩略图、原图、来源页、发布者、尺寸和风险标记。风险标记包括使用权未核验、可能含水印、可能含第三方品牌和低分辨率；系统不替用户作版权结论。
- 候选 URL 只接受无账号凭据的 HTTPS 公网地址，同时解析域名并拒绝指向本机、私网、链路本地地址的结果，避免恶意 URL 和内网探测。
- 商品编辑页增加三图候选卡片、来源跳转、风险标签和二次确认。用户明确确认后才把原图链接填入商品图片。
- 新增 `ai_draft_meta` JSON 字段，保存所选图片原始链接、来源页、Provider、风险标记和用户确认时间；新数据库初始化和旧数据库幂等迁移均已覆盖。
- 新增图片检索次数、状态、延迟和候选数量 Prometheus 指标；SerpAPI Key 通过环境变量注入，异常信息不会回显包含 Key 的请求 URL。

### 达到的效果

- 无图用户可以在同一个商品编辑页搜索并选择最多 3 张相关图片，也可以继续上传自有图片。
- 输入不完整时 Image Scout 只返回追问，不请求真实 Provider；无配置、无结果和上游失败都有明确状态。
- 每个可选候选都有完整原图链接和来源页，并始终显示“使用权未核验”提示。
- 系统不下载、不修改、不去水印，也不声称图片已经获得授权；是否使用及后续责任由用户自行决定。
- 搜索图片的选择和风险确认能够随商品保存，为后续发布门禁提供可追溯证据。
- M3 完成后的全量回归中，Python 190 项、Java 51 项、前端 34 项测试及生产构建全部通过。

## 4. 保存商品等于直接发布

### 遇到的问题

当前前端保存前只检查名称、品类和价格，后端创建或更新商品时直接写入 `published`。描述、图片、待确认内容和合规状态不能阻止半成品发布。

### 使用的技术

- 持久状态只保留 `draft` 和 `published`；“可以发布”由服务端实时计算，不新增持久化 `ready` 状态。
- 商品创建与普通保存一律落为 `draft`；创建、更新 DTO 允许半成品安全保存，不再用发布字段校验阻断草稿。
- 新增服务端 `publish-check`、`publish` 和 `unpublish` 接口；发布与已发布商品修改都会重新运行同一套门禁，前端无法绕过。
- 发布门禁检查商品名、品类、有效价格、详情、图片、搜索图片来源确认、阻断级待确认项、合规结果和最新输入体检；Agent 不可用时失败关闭。
- 本地上传图片直接通过来源检查；搜索图片必须匹配已保存的原图链接、来源页和用户确认记录。
- 草稿只允许店铺所有者读取；公共商品流、购物车、订单与交易入口只接受 `published` 商品，避免草稿泄露或被购买。
- 前端拆分“保存草稿 / 检查并发布”动作，展示服务端结构化阻断原因；发布前再次由用户明确确认。
- 发布成功后进入独立成功页，提供查看商品、继续编辑和返回我的商品三个动作；“我的商品”同时展示草稿与已发布商品。
- 旧数据库启动时幂等增加草稿元数据列、把默认状态改为 `draft`，保留既有 `published`，并把旧 `rejected` 安全迁移为草稿。
- Docker Compose 中 Agent 仅开放内部端口；后端镜像使用 Maven 构建缓存和网络重试，JWT 示例配置满足至少 32 字节要求。

### 达到的效果

- 未完成商品可以安全保存并继续编辑。
- 缺少关键事实、图片、确认或合规条件的商品会返回具体 `publish_blockers`，无法进入发布状态。
- 所有条件通过后仍由用户明确确认发布，AI 不自动替用户决定；发布后仍可编辑或下架为草稿。
- 真实浏览器验收已覆盖：空草稿保存、空草稿发布拦截、完整商品上传图片、确认发布、发布成功页、继续编辑、我的商品状态和买家商品流可见性；草稿未出现在买家商品流，页面无控制台错误。
- 自动化回归结果：Python 190/190、Java 51/51、前端 34/34；前端生产构建和 Docker Compose 三服务镜像构建通过。

## 5. 平台风格只是通用提示词，一次还生成五个平台（M4）

### 遇到的问题

- 通用风格 Agent 混合五个平台规则，即使只选择一个平台，仍在后台构造另外四份预览。
- 拼多多模板默认强调限时抢购，京东与苏宁模板容易引出自营、物流、安装或保修承诺；小红书降级模板把所有品类写成穿搭。
- 无法从已保存商品追溯本次规则版本；任务恢复、商品回填和平台切换存在旧稿与新平台混用风险。
- 旧流程先审查通用稿，再生成平台稿，审查的内容和最终交付不一致。

### 使用的技术

- 独立 JSON Skill 注册表，五份规则分别定义标题编辑预算、搜索词布局、语气、卖点、详情层级、禁用表达、样例、来源与版本。只为目标平台加载系统提示词，单次请求只调用一个平台 Skill。
- Pydantic 严格校验统一 `ProductDraft`：只允许一个标题、不超过五条卖点；错类型、额外字段、多标题和模型伪造版本均不直接进入交付。
- 每请求注入平台系统提示词，不修改共享 Agent 实例，防止并发任务串用规则。
- 商家原始事实是唯一商品事实源，模型底稿与市场研究不作为事实证据；结构化表单保留原值，长段描述允许提取能够在原文逐字核对的规格、人群和场景。
- 风险表达、新增数字、未知项与市场热词在交付前过滤；未确认信息独立进入 `pending_confirmations`。模型失败仅返回原始事实组成的保守稿，不向用户透出 Provider 原始错误。
- LangGraph 调整为事实底稿 → 平台 Skill → 最终稿合规审查，无额外模型调用。
- 独立 `/product/copy` 也输出选定平台的统一稿，内部为事实底稿 + 平台 Skill 两次模型调用；该精简入口不执行市场调研或最终合规审查。
- API、编排结果、SSE/任务恢复和商品元数据携带 `platform_skill_id`、`platform_skill_version`；Java 现有 JSON 字段可直接透传，无新增数据库列。
- 独立风格预览接口复用输入门禁；非法平台在免费预检阶段返回错误，Java 不扣金币、不启动生成。
- 前端仅展示/保存所选平台，保留旧稿的平台身份；切换平台需重新生成，不自动调用或收费；旧历史数据没有版本时明确显示未记录。
- 发布门禁同时比较商品平台与已记录的生成平台，不允许把旧平台稿直接按新平台发布；历史无 Skill 记录的商品仍可正常编辑。

### 风格研究依据与边界

- Google 浏览器页面连续超时，本次改用联网检索读取官方资料，并将来源和核对日期写入每份 Skill。
- 淘宝：[阿里开放平台商品 Schema 示例](https://open.alitrip.com/docs/api.htm?apiId=53973&source=search)，参考标题字段限制；搜索词组织为项目编辑设计。
- 京东：[全球购平台规则](https://global.m.jd.com/rules.html)，仅采用如实描述原则；该来源是历史跨境规则，不能当作现行全站标题规范。
- 拼多多：[用户服务协议](https://www.yangkeduo.com/pdd_user_services_agreement.pdf)，商品描述与活动条件据实表达；短句、配置前置是项目设计。
- 苏宁：[官方商品页](https://www.suning.com/)与[规则中心](https://rule.suning.com/)，参考型号和参数的组织方式；不采用已失效的历史规则，不默认服务权益。
- 小红书：[社区公约 2.0](https://pgy.xiaohongshu.com/help/detail?id=1eda0a065dd894063c2e029a49e8f6a1&userType=4)，强调真实表达、商业身份透明、避免标题党；场景化结构为项目设计。
- 当前标题预算（淘宝30、京东60、拼多多40、苏宁60、小红书20个 Unicode 字符）属于 Jmall 保守编辑约束，不保证满足每个平台每个类目的外部发布要求。

### 达到的效果

- 每次任务交付且保存一个平台的主稿，其他平台既不调用也不构造预览。
- 五份规则、独立样例和统一字段契约可单独回归；最终合规审查覆盖真正交付的稿件。
- 首轮真实 Qwen Plus 五平台接口走查均返回 HTTP 200、正确 Skill 版本且未触发模型降级；发现“挺括”“保障安全”等无依据性能扩写后，补充约束、确定性拦截与回归用例。
- M4 自动验收：Python 247 项、Java 55 项通过；前端原有 42 项通过，浏览器发现规格被旧合并逻辑重复追加后，修复并新增组件级回归测试（1 项通过）。前端生产构建通过。
- 2026-08-31 浏览器实测：真实拼多多 Skill 单稿交付；独立测试草稿的人工副标题和规格保存重开后保留；连续应用两次不再重复规格；切到京东保留拼多多 Skill 身份并要求重新生成。只创建演示商家的验收草稿，未发布。
- 模型事实过滤是防线而非真实性保证，仍需商家核对与发布门禁。

## 6. 追问泛化、转化过程不可观测（M5）

### 遇到的问题

- 所有品类使用同一句“补充规格”的追问，用户不知道应该填写什么。
- “AI 检查并生成”达到门槛就启动模型，缺少只检查、零模型费用的独立操作。
- LLM Token/成本不能说明用户在哪一步流失；重复复检、SSE 恢复和发布预检容易被误计为新转化。
- Java 已有 Prometheus 抓取配置，但没有 Actuator/Prometheus 运行依赖，业务漏斗没有数据出口。

### 使用什么技术解决

- 确定性六品类模板与别名映射，围绕缺失事实/人群追问，最多三个问题，不用 LLM，也不要求填写全部示例。保温杯补容量/材质等针对性提示；未知品类回退通用模板。
- 前端增加独立免费体检，保留草稿及人工修改；并发点击保护、表单变化后丢弃过期体检结果。
- Python 增加输入检查、生成启动与终态、首次进度、Skill 追溯/降级指标；终态和首次进度只计一次，图片输入不足不压低搜索 P95。
- Java Micrometer + Actuator 输出有限标签指标；编辑会话按临时 UUID 和用户上下文去重（ID 不进入标签），固定阶段、前置阶段验证、容量/TTL 限制；服务端商品事件仅在实际写入且事务提交后计成功。
- Grafana 面板分别展示编辑会话转化、真实保存/发布事件与技术耗时，不把客户端事件当作 DB 审计。
- 增加统一 v0.2 自动回归及人工演示入口，不复用会充值/下单的旧 E2E 脚本。

### 达到了什么效果

- 浏览器验证食品类只填名称/品类时出现两条具体追问；补“原味、净含量200克、办公室上班族”后免费检查通过，没有 LLM/生成启动指标。
- 容器内 50 次 HTTP 免费检查样本：全部正确拦截少量输入，P95 0.88ms（本地样本，非公网或生产 SLA）。
- 完整回归入口实际执行成功：Python **296** 项、Java **70** 项、前端 **48** 项，均无失败；TypeScript 检查/生产构建通过。六品类双路径显式验收集 12/12 正确放行，六品类标题/品类简略输入 6/6 拦截；既有对抗输入、图片风险、平台版本和发布门禁测试全部保持通过。这是有限测试集，不代表开放输入的错误放行率绝对为零。
- 本机 Maven/JRE 不可直接运行，最终改用 Docker Maven 完成全部 Java 测试，而非把旧报告当新结果。
- 最终服务已重建：Java `/actuator/health` 为 UP，Prometheus 中 Java/Agent `up=1`；未登录上报接口返回 401，`/actuator/env` 返回 404；11 条 Grafana 查询逐条经 Prometheus API 校验成功。
- Grafana 浏览器验收通过：`Jmall v0.2 产品漏斗` 已自动加载，实际显示测试会话保存率 1/1、发布 0/1、无图解决 0/1，并显示服务端计数曲线；未发生的生成/搜索保持无数据，不伪造结果。
- 浏览器实际事件：新编辑会话 `editor_opened=1/no_image=1`；点击无图商品的“检查并发布”后 `draft_saved=1`、服务端 `draft_created=1/publish_blocked=1/published=0`，没有把检查当发布成功。只新增 M4/M5 两份演示商家验收草稿，均未发布。
- 保留既有前端大 chunk 提示和 Go 指标未接通状态；真实线上转化率、跨日留存、生产负载下 P95 尚无数据，不在本次声称已达标。

## 7. 结项复核：输入语义门禁漏判（已修复并复验）

### 遇到的问题

- 2026-08-31 原有 414 项回归通过，但进一步补测发现“很棒；喜欢”“材质未知；容量未知”“不知道呢”和包含否定事实的段落都得到 ready=true、85 分。

## 8. 生成结果缺副标题、营销信息不足、搜图时机过早（体验收尾）

### 遇到的问题

- 商品实体和页面已有副标题字段，但最终平台 Skill 会把缺少逐字事实依据的副标题清空，导致完整 Agent 跑完后仍为空。
- 目标人群与 SEO 使用了和材质、规格相同的事实防护，联网调研得到的安全营销信息也被全部移除；用户输入少时无法得到合理扩充。
- Image Scout 入口位于图片区域，只检查基础输入是否完整，无法保证搜索使用的是本轮 AI 完善后的副标题、人群和 SEO。
- compose 只读取旧别名 `JMALL_SERPAPI_API_KEY`，用户按标准名配置 `SERPAPI_API_KEY` 后运行容器仍然拿不到密钥；前端 Docker 构建还会错误复制本机 `node_modules`。

### 使用什么技术解决

- 平台 Skill 无论模型是否返回副标题，都会用商家已确认的描述、规格和场景生成非空副标题；模型副标题仍经过事实、数字和风险词校验。
- 将字段边界拆分为“商品事实”和“营销扩充”：材质、规格、功效、服务承诺仍只能来自商家事实；只有带来源的市场调研可追加最多 3 个低风险人群并扩充 8–12 个 SEO 词。儿童、孕妇、患者等敏感人群和爆款、功效、未确认属性不得从热词进入可发布内容。
- 输出 `marketing_enrichment`，记录来源 URL、联网调研是否实际使用、是否扩充人群/SEO、是否生成副标题。
- 搜图按钮移动到“免费检查信息 / AI 检查并生成”旁边；只有生成成功、非降级模板、无已有图片且表单与生成完成快照完全一致时启用。处理函数内部重复门禁，表单修改或搜索过程中变化都会丢弃旧结果。
- 搜图请求增加副标题、使用场景和 SEO；Python/Java 完成字段接收与 camelCase 兼容。compose 同时支持标准名和旧别名，优先 `SERPAPI_API_KEY`；前端新增 `.dockerignore` 排除依赖和构建产物。

### 达到了什么效果

- 五个平台的完整输入均得到非空副标题和 8–12 个去重 SEO 词；有来源的人群扩充会保留商家原人群并追加安全分群，不会覆盖原输入。
- 新增测试验证：无副标题模型输出、联网人群/SEO 扩充、敏感人群和虚构属性拦截、搜图按钮位置、生成后启用、编辑后失效、函数级门禁及完善字段透传。
- 全量回归：Python **366**、Java **70**、前端 **52**，合计 **488** 项通过；TypeScript 与 Vite 生产构建通过，三端 Docker 镜像完成重建。
- 运行中的 Agent 已读取 `SERPAPI_API_KEY`，原 `/app/data/merchant_ai_store.json` 在重建前备份并恢复；新增 `jmall_agent_data` 命名卷，后续重建不会再丢 Agent 本地数据。唯一一次真实请求正确进入 `serpapi_google_images` 且输入门禁通过，但 SerpAPI 返回 HTTP 401；当前 52 字符、非十六进制密钥需要在 SerpAPI 控制台重新核对，未重试。

## 9. 千问图片搜索配置与模型能力边界

### 遇到的问题

- 用户已将图片模型写入小写环境变量 `picture_base=qwen3.7-flash`，并希望复用既有千问 Key 与 `QWEN_BASE_URL`，原实现却只支持 SerpAPI。
- 普通联网搜索结果是文字，不等于可展示的图片候选；若没有真实图片 URL，不能把文字结果或模型猜测的 URL 当作搜图成功。
- 图片搜索请求携带真实 API Key，必须避免把 Key 发送到自定义或恶意地址，也不能在异常信息中泄露上游响应正文。

### 使用什么技术解决

- 增加 `QwenWebImagesProvider`，使用 OpenAI-compatible Chat Completions 的 `enable_search` 与 `enable_text_image_mixed`；只解析响应中的 HTML `img` 或 Markdown 图片，不生成、不下载、不去水印。
- `picture_base`、`PICTURE_BASE` 与 `IMAGE_SEARCH_MODEL` 都映射到独立的图片模型配置，不与普通对话模型混用。Compose 默认选择 Qwen，并复用 `JMALL_QWEN_API_KEY`、`QWEN_BASE_URL`。
- API Key 只放在 Authorization header；Provider 仅允许 HTTPS 的 `aliyuncs.com` 地址，HTTP 状态、无效 JSON、超时与纯文字结果均转为不含 Key 的结构化错误。
- 保留 SerpAPI Provider 作为可选项。模型返回图片后继续复用既有 HTTPS、DNS、私网地址、去重、最多三张和风险标注防线。
- 当千问完成联网检索但未返回图片时，返回明确的模型能力错误，不再误报为“这个商品没有图片结果”。

### 达到了什么效果

- 配置、请求体、HTML/Markdown 图片解析、端点保护、Key 脱敏、纯文字能力错误和 Provider 工厂均有 MockTransport 回归用例。
- 全量回归：Python 374、Java 70、前端 52，共 496 项通过；TypeScript 与 Vite 生产构建通过。
- 运行中的 Agent 已确认读取 `qwen_web_images / qwen3.7-flash / dashscope.aliyuncs.com`，且 Qwen Key 非空；Agent `/health`、Java Actuator 和前端均正常。
- 唯一一次真实千问请求鉴权和接口调用成功，但返回 0 个图片候选。阿里云官方当前确认 `qwen3.7-flash` 支持联网搜索，却没有将其列入图文混排支持模型；因此该配置只能记为“接入成功、真实图片能力未通过”。可改用官方列出的 `qwen-flash`，或继续使用结构化图片搜索 Provider。
- 按产品决定改用 `qwen-flash` 后再次执行一次完整 Image Scout 真实验收：模型请求成功且 Provider 未报能力错误，说明返回内容中存在可解析图片；但候选经过 HTTPS、公开 DNS、来源完整性与风险过滤后剩余 0 张，最终为 `no_results`。因此仍未达到“至少 1 张可展示安全候选”的发布门槛，没有提交、合并或推送 v0.2。
- 最终切换到阿里云明确支持图文混排的 `qwen-plus-latest`。单次真实完整验收返回 `ready`，得到 1 张 `img.alicdn.com` HTTPS 候选；公网 DNS、安全过滤与风险标注全部通过，图片风险仍标记为授权、视觉和分辨率未核验。该结果达到本轮“至少 1 张安全可展示候选”的发布门槛。

## v0.2 完成标准

- 只输入商品名和品类时，系统返回信息体检和最多 3 个问题，不生成完整详情页。
- 达到信息门槛后，系统生成一份只使用已确认事实的主草稿。
- 未上传图片且信息完整时，系统能够返回最多 3 个带原始链接、来源页和风险提示的图片候选。
- 使用搜索图片前必须明确确认风险，系统保存来源与确认时间，但不替用户判断授权。
- 商品默认保存为草稿，只有通过后端发布检查后才能进入 `published`。
- 为以上流程补充 10 至 15 个主要品类和失败场景测试。
