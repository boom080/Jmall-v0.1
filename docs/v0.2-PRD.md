# Jmall v0.2 产品需求文档

> 文档状态：M1–M5 功能已实现；副标题、营销扩充与完善后搜图已收尾，488 项自动回归通过；真实 SerpAPI 因当前 Key 返回 401 待复验  
> 版本定位：从“AI 技术链路跑通”进化为“商家能完成一件商品草稿”  
> 计划版本：v0.2  
> 更新日期：2026-09-01  
> 核心原则：先理解完整，再生成；先形成草稿，再由用户发布

## 1. 一句话定义

Jmall v0.2 是一个面向小商家的 AI 商品上架助手：它先判断商家是否已经说清楚“卖什么、真实特点是什么、卖给谁”，信息不足时只追问，信息完整后才启动 Agent，最终交付一份可编辑、有图片、有发布门禁的商品草稿。

## 2. 背景与核心问题

v0.1 已经证明 Multi-Agent、RAG、市场调研、文案、合规检查、平台风格适配和 SSE 任务恢复能够工作，但当前产品闭环仍然不成立：

1. 用户只输入商品名和品类，系统仍然生成完整标题、卖点和详情，结果看似完整但缺少真实依据。
2. 系统知道信息不足，却不能把缺口转换成用户容易回答的问题。
3. 用户没有商品图片时无法继续，只能看到占位图或无效的图片生成入口。
4. 保存商品会直接进入 `published`，草稿、检查和发布没有清晰边界。
5. AI 输出很多，但用户真正需要的是一份能够检查、修改和发布的主草稿。

因此，v0.2 不继续扩展 Agent 数量，而是补齐一条最短可用链路：

```text
表达商品意图
    ↓
免费信息体检 ──信息不足──→ 最多 3 个追问 → 用户补充 → 重新体检
    ↓ 信息完整
生成一份主草稿
    ↓
上传图片 / 选择 3 个搜索候选之一
    ↓
保存草稿 → 发布检查 → 用户确认发布
```

## 3. 产品目标

### 3.1 P0 目标

- 阻止少量、重复、占位或无意义输入启动完整 Agent。
- 支持用户通过一段自然语言或现有结构化表单表达完整商品意图。
- 信息不足时返回系统已理解内容、缺失内容和最多 3 个具体问题。
- 信息完整后只生成一份目标平台主草稿，保留用户提供的真实事实。
- 用户无图时提供最多 3 个带原始来源的搜索候选，系统只负责查找和展示。
- 商品默认保存为草稿，通过服务端发布检查并由用户确认后才公开。
- 免费预检不扣金币；任何付费入口都必须在扣费前复检。

### 3.2 P1 目标

- 针对重点品类生成更具体的补充问题。
- 记录用户从信息不足到生成成功的转化漏斗。
- 展示 AI 使用了哪些商家事实，让用户能够定位和纠正误解。

### 3.3 非目标

- 不做无人值守的自动发布。
- 不做自动定价、自动促销或自动承诺销量。
- 不做批量铺货和多店铺运营。
- 不增加复杂的多轮聊天工作台；v0.2 仍以商品编辑页为中心。
- 不提供删除第三方图片水印的能力。
- 不代替用户完成图片版权授权判断；系统保留原始来源和风险提示，由用户自行决定是否使用。

## 4. 目标用户与使用场景

### 4.1 目标用户

- 第一次使用 AI 上架商品的小商家。
- 有商品但不擅长写电商文案的商家。
- 能说清楚商品特点，但不愿填写大量专业表格的用户。

### 4.2 核心场景

#### 场景 A：用户习惯自然表达

用户填写商品名和品类，并输入一段话：

> 我想卖一款采用食品级 304 不锈钢的 500ml 保温杯，杯盖可拆洗，支持 12 小时保温，主要卖给学生和上班族。

系统识别商品事实和目标人群，允许开始生成；使用场景未填写时可以生成，但完整度不是 100%。

#### 场景 B：用户习惯填写表格

用户填写商品名、品类、两项以上真实规格和目标人群。描述可以较短，系统合并所有结构化字段后判断是否完整。

#### 场景 C：用户输入太少

用户只填写“保温杯 / 水具”。系统返回 `needs_input`，展示已理解的商品名和品类，并追问真实规格和目标人群，不启动任何模型 Agent，也不扣金币。

#### 场景 D：用户没有图片

商品信息达到门槛后，Image Scout 根据已确认事实搜索候选。系统展示原图、来源页和风险提示；用户可以选择其中一张、上传自有图片，或暂时保存无图草稿。图片是否具备使用授权由用户自行负责。

## 5. 功能需求

## 5.1 商品信息体检

### 5.1.1 输入方式

系统必须合并以下输入，不得只读取商品描述：

- 商品名称。
- 商品品类。
- 商品说明 / 一段话需求。
- 规格或真实事实。
- 目标人群。
- 使用场景。
- 价格仅参与商品草稿和发布检查，不作为启动 Agent 的必要条件。

### 5.1.2 硬门槛

启动完整 Agent 必须同时满足：

1. 有效商品名称。
2. 有效商品品类。
3. 至少两项去重后的真实事实，或一段包含明确事实标记、参数或计量值的具体描述。
4. 有效目标人群。

使用场景是加分项，不是硬门槛。原因是部分商品的目标用户非常明确，但不存在唯一使用场景。

以下内容不得作为有效信息：

- `测试商品`、`商品`、`参数`、`规格`、`不知道` 等占位内容。
- 重复复制的长句。
- `好用；好用` 等重复或纯主观卖点。
- 单字、零宽字符、纯 Emoji 或只包含标点的内容。
- “请商家确认”“待补充”等 AI 占位模板。

### 5.1.3 输出状态

`ready`：允许进入付费 Agent。  
`needs_input`：不启动后续 Agent，只返回体检结果。

体检结果至少包含：

- `score`：0 到 100 的透明清单分数。
- `understood`：系统已经识别的事实。
- `missing`：阻止生成的缺失项。
- `questions`：最多 3 个补充问题。

### 5.1.4 安全与计费

- 浏览器先调用免费体检接口。
- Java 付费编排接口在扣金币前必须重新体检，避免绕过前端。
- Python LangGraph 在任何模型节点前再次体检，形成最后一道硬门禁。
- 体检服务不可用时失败关闭，不允许降级为直接生成。
- 页面预检和 Agent 运行期间禁止重复点击，避免重复任务与重复扣费。

## 5.2 补充问题

### 5.2.1 基础规则

- 每次最多显示 3 个问题。
- 问题必须对应具体缺失字段，不输出“请提供更多信息”之类泛化提示。
- 用户不需要进入独立聊天页，直接修改现有表单后重新检查。
- 重新检查不运行市场调研、RAG 和文案 Agent。

### 5.2.2 P1 品类问题模板

优先支持以下品类：食品饮料、服饰鞋包、家居日用、数码家电、美妆护肤、运动户外。

示例：

- 保温杯：容量、材质、保温时长、适用人群。
- 服饰：材质、尺码范围、版型、适用人群。
- 食品：净含量、成分或口味、保质期、适用人群。
- 数码：型号、关键参数、兼容范围、适用用户。

## 5.3 Agent 生成与交付

### 5.3.1 启动条件

只有体检状态为 `ready` 时才启动：意图解析、市场调研、RAG、文案、合规和平台风格适配。

### 5.3.2 主草稿

默认只交付当前目标平台的一份主草稿，包含：

- 商品标题。
- 副标题。
- 3 至 5 个核心卖点。
- 商品详情。
- 规格信息。
- 目标人群。
- 使用场景。
- 8 至 12 个平台化 SEO 搜索词。
- 合规状态与待确认项。

一次任务只生成用户当前选定平台的内容，不生成、不预览其他平台版本。

### 5.3.3 平台 Skill 路由

- 用户在启动 Agent 前必须选定一个目标平台。
- 编排 Agent 根据 `target_style` 只调用一个平台专用 Skill，不使用一套通用 Prompt 强行改写所有平台。
- v0.2 平台 Skill 映射：`taobao_listing_v1`、`jd_listing_v1`、`pinduoduo_listing_v1`、`suning_listing_v1`、`xiaohongshu_listing_v1`。
- 每个 Skill 独立定义标题长度、搜索词布局、语气、卖点结构、详情层级和平台禁用表达。
- 平台 Skill 必须输出统一的商品草稿 Schema，但内容规则彼此独立。
- 未支持的平台必须在免费检查阶段拦截，不得收费后降级成通用风格。
- 交付结果记录 `platform_skill_id` 和 `platform_skill_version`，便于回归和追溯。

### 5.3.4 事实约束

- 商家输入的事实必须完整传递给编排 Agent。
- 模型不能新增未经用户确认的材质、认证、销量、折扣、成分、功效和价格承诺。
- 无依据内容必须进入 `pending_confirmations`，不能混入可发布正文。
- 用户能够看到“AI 使用的事实”与“仍需确认的内容”。
- 副标题必须由已确认事实概括，完整生成成功后不得为空。
- 联网调研只能扩充目标人群定位和 SEO；必须保留来源、保留商家原人群，且不能把热词变成材质、规格、功效或服务承诺。
- 儿童、孕妇、患者等敏感适用人群没有商家确认时不得自动追加；爆款、销量、认证、功效和未确认属性不得进入 SEO。

## 5.4 无图处理与 Image Scout

### 5.4.1 触发条件

- 用户已有上传图片：不自动搜索。
- 用户无图、完整 Agent 已成功生成，且表单自生成后未修改：允许启动 Image Scout。
- 商品信息不足：不搜索，避免根据模糊标题返回无关图片。
- 生成后任一表单字段被编辑：旧完成态失效，必须重新生成后才能搜索。

### 5.4.2 搜索策略

搜索词由完善后的商品名、副标题、品类、真实规格、目标人群、场景和 SEO 组成。Image Scout 调用配置的图片搜索 Provider，Google 图片搜索可作为默认搜索源。系统的责任边界是“找到并展示相关图片”，不对图片版权或商业使用权做保证。

### 5.4.3 候选卡片

最多展示 3 个候选，每个候选必须包含：

- 缩略图。
- 来源网站和来源页面链接。
- 作者或发布者。
- 原始图片链接。
- 是否检测到水印、竞品品牌、低清或来源缺失等风险。
- `使用此图` 操作，并明确提示“请自行确认图片使用权”。

如果不足 3 张相关候选，如实展示实际数量，不使用无关图片补足。

### 5.4.4 水印与版权边界

- 系统不得移除第三方图片水印。
- 系统不修改、不去水印、不声明搜索图片具有授权。
- 用户点击“使用此图”前必须确认风险提示，其后续使用行为由用户自行负责。
- 系统只保存用户选择的原始链接、来源页、风险标记和确认时间，不在搜索阶段代替用户下载或加工图片。
- 展示远程图片前校验 URL 协议、跳转地址和内网地址，防止 SSRF 与恶意跳转。

## 5.5 草稿与发布

### 5.5.1 状态规则

v0.2 只保留两个持久状态：

- `draft`：商家可编辑，买家不可见、不可购买。
- `published`：通过服务端检查并由商家确认，买家可见、可购买。

“可以发布”是实时检查结果，不新增持久化 `ready` 状态，以控制小版本复杂度。

### 5.5.2 用户动作

商品编辑页提供两个清晰动作：

- `保存草稿`：允许缺图或存在缺失项，不公开商品。
- `检查并发布`：调用服务端发布检查；通过后再次由用户确认发布。

AI 不得自动触发发布。

### 5.5.3 服务端发布门禁

发布必须满足：

- 商品名称、品类和大于 0 的价格有效。
- 商品信息体检为 `ready`。
- 商品详情非空。
- 至少一张用户上传或明确确认使用的搜索图片。
- 不存在阻断级 `pending_confirmations`。
- 合规审查状态不是 `rejected`。

发布失败时返回结构化 `publish_blockers`，前端定位到对应表单区域。

### 5.5.4 发布成功页

商品发布成功后进入独立成功页，不直接跳回编辑表单。页面展示商品缩略预览和“发布成功”状态，并提供三个动作：

- `查看商品`：打开买家侧商品页。
- `继续编辑`：打开已发布商品编辑页。
- `返回我的店铺`：进入已发布商品管理列表。

### 5.5.5 已发布商品编辑

- 用户可以在“我的店铺”中编辑已发布商品。
- 编辑页加载当前线上内容，未保存前不影响已发布商品。
- 点击“保存修改”时，服务端重新执行发布门禁；通过后更新内容并保持 `published`。
- 修改后不再满足发布条件时，拒绝覆盖线上商品并展示阻断项；用户可另行选择“下架并保存为草稿”。

## 6. 页面与交互

商品编辑页保持单页结构，分为三个区域：

1. `告诉 AI 你要卖什么`：商品名、品类、一段话需求、规格、人群和场景。
2. `AI 上架助手`：完整度、已理解内容、缺失项、追问和 Agent 进度。
3. `商品草稿`：主文案、图片候选、合规提示、保存草稿与发布动作。

关键状态：

| 状态 | 主按钮 | 页面反馈 |
|---|---|---|
| 尚未检查 | AI 检查并生成 | 显示输入示例 |
| 正在检查 | 检查中 | 禁止重复点击 |
| 信息不足 | 重新检查 | 展示缺失项和最多 3 个问题 |
| Agent 运行中 | 生成中 | 展示阶段进度并支持断线恢复 |
| 草稿已生成 | 保存草稿 / 检查并发布 | 展示主草稿、图片和发布阻断项 |
| 发布成功 | 查看商品 / 继续编辑 / 返回我的店铺 | 显示独立发布成功页 |

## 7. 接口与数据约定

### 7.1 已有并保留

#### `POST /api/ai/input-assessment`

免费，不扣金币。

```json
{
  "productInfo": {
    "title": "轻量保温杯",
    "category": "水具",
    "description": "我想卖一款……",
    "specifications": "304不锈钢；500ml",
    "targetAudience": "学生和上班族",
    "usageScenarios": "通勤"
  }
}
```

```json
{
  "input_assessment": {
    "status": "ready",
    "ready": true,
    "score": 100,
    "understood": [],
    "missing": [],
    "questions": []
  }
}
```

#### `POST /api/ai/orchestrate/stream`

只有服务端复检为 `ready` 后才扣费并启动任务。输入不足时返回 `needs_input` 事件，不创建付费 Agent 任务。

### 7.2 v0.2 新增

#### `POST /api/ai/images/candidates`

返回最多 3 个图片候选及原始图链接、来源页和风险标记；不替用户做授权判断。

#### `POST /api/products/{id}/publish-check`

只检查，不改变状态，返回 `publishable` 与 `publish_blockers`。

#### `POST /api/products/{id}/publish`

再次执行相同服务端检查，通过后将商品状态改为 `published`。

### 7.3 数据模型

`jmall_product.status` 复用现有字段，创建和普通更新默认写入 `draft`。

新增一个 `ai_draft_meta` JSON/TEXT 字段，集中保存：

- `input_snapshot`：用户原始描述和结构化事实。
- `input_assessment`：生成时的体检结果。
- `pending_confirmations`：仍需用户确认的内容。
- `selected_image_source`：所选图片的原始链接、来源页、风险标记、用户确认时间。
- `platform_skill_id` / `platform_skill_version`：本次生成实际使用的平台 Skill。

这样可以避免为 v0.2 增加过多独立字段，同时保留发布检查所需的证据。

## 8. 指标与可观测性

### 8.1 核心产品指标

- 只输入标题和品类时，完整 Agent 启动率必须为 0%。
- `needs_input` 请求的金币扣除率必须为 0%。
- 有效长段落与有效结构化表单的正确放行率目标不低于 90%。
- 对抗输入错误放行率必须为 0%。
- 进入编辑页后成功保存草稿的比例。
- 草稿通过发布检查并发布的比例。
- 无图用户成功选择图片或上传自有图片的比例。

### 8.2 技术指标

- 免费体检不产生 LLM Token。
- 免费体检 P95 响应时间低于 300ms，不含公网网络波动。
- Agent 首个进度事件 P95 低于 3 秒。
- 图片搜索 P95 低于 8 秒。
- 重复点击导致的重复任务数为 0。
- 所有候选图片的原始链接与来源页完整率为 100%。
- 用户选择搜索图片时，风险提示确认记录率为 100%。
- 每份主草稿的 `platform_skill_id` 和版本记录率为 100%。

## 9. 验收标准

### 9.1 输入体检

- 只输入商品名和品类时返回 `needs_input`。
- 有效长段落“商品事实 + 目标人群”可以通过。
- 有效“规格 + 目标人群”结构化输入可以通过。
- 重复长句、重复规格、占位符、无效人群、零宽字符和纯 Emoji 不能通过。
- 最多返回 3 个问题。
- 前端、Java 和 Python 三层均无法绕过门禁。
- 输入不足或体检服务异常时不扣金币。

### 9.2 图片

- 有图时不触发搜索。
- 无图时最多返回 3 个带原始图链接和来源页的候选。
- 系统不移除水印、不修改原图、不声明图片已获授权。
- 用户点击使用前能看到来源和风险提示，并完成明确确认。
- 少于 3 个相关候选时不使用无关图片补齐。

### 9.3 草稿与发布

- 新建和普通保存不会直接公开商品。
- 缺少详情、图片或存在阻断项时，服务端拒绝发布。
- 绕过前端直接调用发布接口仍然会被服务端拒绝。
- 发布必须由用户明确确认。
- 买家列表、购物车和下单链路只接受 `published` 商品。
- 发布成功后进入独立成功页，可查看商品、继续编辑或返回我的店铺。
- 在“我的店铺”中可编辑已发布商品；修改通过发布门禁后保持 `published`。
- 不合格修改不得覆盖当前线上内容。

### 9.4 平台 Skill

- 每次任务只调用一个目标平台 Skill，不生成其他平台内容。
- 五个已支持平台均有独立 Skill 和回归样例。
- 不支持的平台在扣费前拦截。
- 交付结果可追溯到具体 Skill 及版本。

## 11. 已确认产品决策

1. 使用场景作为加分项而不是硬门槛，最低闭环为“卖什么 + 真实特点 + 卖给谁”。
2. Image Scout 只负责搜索和展示图片，保留来源并提示风险；是否使用及后续责任由用户自行决定。系统不移除水印。
3. v0.2 持久状态只保留 `draft` 和 `published`，发布就绪状态实时计算，不新增 `ready` 状态。
4. 发布后进入独立成功页；用户可从“我的店铺”编辑已发布商品，通过服务端发布检查的修改保持 `published`。
5. 一次只生成一个目标平台的内容；编排 Agent 根据平台专门调用对应 Skill，不同平台 Skill 互相独立。
