# 6.2 Jrunmall 面试问答

## 30 秒项目介绍

Jrunmall 是一个本地电商 AI 应用项目，前端包含 Vue3 用户端和商家端，后端以 Java/Spring Boot 为主，AI 能力由 Python FastAPI 服务承接。项目完成了商品浏览、购物车、下单、模拟支付、订单查询、商家商品管理，以及商家端 AI 文案生成和 RAG 知识库检索。它不是线上商用项目，重点是展示电商业务闭环和 AI/RAG 工程落地。

## 1 分钟项目介绍

Jrunmall 的业务侧包括用户注册登录、地址管理、商品列表和详情、购物车、下单、模拟支付、订单查询，也包含商家端商品管理、普通订单和秒杀订单查看。AI 侧通过 Java AI Adapter 把商品服务和 Python `ai-services` 解耦，商家可以上传 txt 创建知识库，或导入文本/PDF 文档，服务会切 chunk、生成 embedding，并写入 PostgreSQL + pgvector。生成商品文案时会带上 `knowledgeBaseId`，只在指定知识库检索 chunk，把命中的内容拼到 prompt，最后返回文案、`response_source`、`usedChunks` 和 `citations` 给前端展示。

## 和普通商城有什么区别

普通商城一般只覆盖商品、购物车、订单等交易链路。这个项目在交易链路之外增加了商家端 AI 能力：商家能维护知识库，用指定知识库辅助生成商品标题、卖点、详情文案和风险提示。它的重点不是把商城做成生产系统，而是把电商数据、商家工作台、Java 后端、Python AI 服务和 RAG 检索串成一个可验证的本地工程。

## RAG 是怎么实现的

流程是：商家端上传或导入文档，Java 接口转发到 Python FastAPI；Python 清洗文本并切 chunk；embedding provider 生成向量；chunk、metadata、embedding 写入 PostgreSQL + pgvector。生成文案时，服务根据商品输入构造 query，生成 query embedding，只在指定 `knowledgeBaseId` 下使用 pgvector 相似度检索，再把命中 chunk 放进 prompt 的证据区。

## 怎么证明不是假 RAG

可以从三点证明：第一，知识库内容来自用户上传或导入，不再依赖固定 fake fallback 数据；第二，检索 SQL 包含 `chunk.knowledge_base_id = :knowledge_base_id` 和 `chunk.embedding <=> cast(:query_embedding as vector)`；第三，响应会返回 `response_source=rag`、`usedChunks` 和 `citations`，前端展示命中的文档、chunk index、分数和内容。如果没有命中，会返回 `no_rag_fallback`，不会伪装成 RAG。

## 为什么用 pgvector

这个项目的 RAG 数据量适合先用 PostgreSQL + pgvector 做本地工程落地。pgvector 可以让知识库表、文档表、chunk 表和向量检索在同一个数据库里维护，降低额外引入向量数据库的复杂度；同时支持 `<=>` 相似度计算和向量索引，后续数据规模扩大时也能继续优化。

## embedding 是什么

embedding 是把文本转换成一组数字向量，用来表示文本在语义空间中的位置。RAG 检索时，会把用户问题或商品信息转换成 query embedding，再和知识库 chunk 的 embedding 做相似度比较，找出最相关的文本片段。

## mock embedding 和真实 embedding 有什么区别

mock embedding 是本地开发用的确定性向量，通常由哈希等方式生成，只能验证上传、切块、入库、检索和引用展示流程是否跑通，不代表真实语义相似度。真实 embedding 来自模型服务，例如 openai-compatible embedding API，同一个模型生成的 query 和 chunk 向量才有语义检索意义。切换真实 embedding 后，旧 mock chunk 需要清空并重新生成。

## 为什么要 Java + Python 分层

Java 负责电商主业务和已有 Spring Boot 模块，Python 负责 AI 服务、LangChain/LangGraph、embedding 和 RAG 相关能力。这样可以让商品、购物车、订单等核心业务保持稳定，同时让 AI 服务独立演进。Java AI Adapter 作为边界层，负责请求转发、模型选择、密钥解析和响应映射。

## Java AI Adapter 做了什么

Java AI Adapter 封装了商品文案生成、模型列表、知识库列表、知识库创建、文档导入和 txt 上传等 AI 相关调用。它把 `gulimall-product` 和 Python `ai-services` 解耦，也支持 LangChain4j/OpenAI-compatible 直连模型配置，并把 Python 返回的 `usedChunks`、`citations` 映射给商品服务和前端。

## 知识库上传后发生了什么

上传 txt 后，商家端把 multipart 请求发给 Java 商品服务，Java 通过 AI Adapter 转发到 Python。Python 创建 knowledge base，读取 UTF-8 文本，清洗后切 chunk，生成 embedding，保存 document 和 chunks，最后返回 `knowledgeBaseId`、`documentId`、`chunkCount`、`embeddingProvider` 和状态。前端刷新知识库列表后可以选择这个知识库生成文案。

## 遇到过哪些问题

- fake RAG：早期知识库依赖 fallback/hardcode 数据，后来清理为上传后入库检索。
- fallback 数据：远端失败时不再用假知识库冒充真实数据，而是显示空列表或 fallback 状态。
- `embedding_json text`：旧结构只是文本 JSON，不适合 pgvector 检索，目标结构改为 `embedding vector(1024)`。
- vector 维度不匹配：mock 默认维度和真实 embedding 维度不同，切换模型后必须重建 chunk embedding。
- `psycopg` 缺失：Python 连接 PostgreSQL 需要安装 `psycopg`/`psycopg2-binary` 依赖。
- `.env.local` 配置：根目录、`ai-services`、`docker/local` 的 env 文件用途不同，不能混用。
- API Key 安全：真实 Key 只写本地 `.env.local`，README 和 docs 只能写占位符。

## 这个项目还有什么不足

它不是生产系统，支付仍是模拟支付；RAG 的检索效果依赖真实 embedding 配置和知识库质量；本地 Docker 初始化步骤较多；部分完整 Spring 上下文测试受本机 MySQL/Redis/PostgreSQL 配置影响；权限、审计、监控、灰度发布、生产级安全策略还没有完整建设。

## 后续怎么优化

后续可以优化知识库删除和多文档追加、chunk 管理、引用来源 UI、RAG 命中评估、真实 embedding 批处理、向量索引策略、AI 请求日志、模型调用成本控制、商家权限隔离，以及端到端自动化验收。

需要补生产环境配置隔离、真实鉴权和权限模型、密钥托管、日志审计、异常告警、限流降级、数据备份、CI/CD、Docker/Kubernetes 部署、HTTPS、前后端安全加固、支付真实接入、订单一致性验证，以及 RAG 数据质量评估和模型输出合规审核。
